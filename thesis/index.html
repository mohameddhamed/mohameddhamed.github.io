Java Virtual Threads in Spring Boot Applications: Empirical Benchmarks on Throughput, Carrier Starvation, and Monitor Pinning Mitigation

Author: Mohamed Hamed • Institution: Eötvös Loránd University (ELTE) • Defense: 2026/2027 • Status: Research Complete (125 Trials)
Monograph Synopsis: This dissertation investigates the runtime mechanics, failure modes, and mitigation patterns of Java 21 Project Loom (JEP 444) Virtual Threads under high-concurrency enterprise workloads. Across 125 reproducible empirical trials on bare-metal Linux hardware, we uncover how unmonitored migration of legacy Spring Boot MVC services introduces catastrophic carrier thread pinning, and demonstrate how lock replacement restores a 261x throughput advantage with sub-2ms P99 latencies.

1. The Core Architectural Problem

Java Virtual Threads decouple logical application tasks from Operating System kernel threads. While platform threads incur ~1MB native stack memory footprints, virtual threads operate as user-mode continuations managed cooperatively by a small ForkJoinPool carrier pool (typically matching the physical core count $N_{\text{CPU}}$).

However, the JVM runtime cannot unmount a virtual thread when blocking I/O occurs within a synchronized block or across a native JNI/FFM boundary (JFR event: jdk.VirtualThreadPinned). When legacy JDBC drivers or enterprise connection pools synchronize around socket read/write calls under heavy load, all carrier threads become pinned simultaneously. At this saturation threshold, the entire thread pool deadlocks, yielding extreme throughput collapse and multi-second latency degradation.

3. Key Empirical Findings

  • Pinning Latency Cliff: When 8/8 carrier threads become pinned by blocking JDBC socket reads, P99 request latency degrades by 780x (jumping from 1.82ms to 1,420ms).
  • Lock Replacement Remediation: Replacing legacy synchronized blocks with java.util.concurrent.locks.ReentrantLock completely eliminates jdk.VirtualThreadPinned events without modifying business logic.
  • Memory Efficiency: 10,000 unpinned Virtual Threads consume only 34MB resident heap memory, compared to 210MB required for 1,000 OS platform threads.
  • ThreadLocal Deprecation: Deep ThreadLocal inheritance under Loom creates severe heap retention leaks; migrating to Java 21 ScopedValue reduces memory footprint by 62%.
